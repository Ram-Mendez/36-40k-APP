# Referencias del formato de trabajo

Consulta: 10/11/2026. Se adaptan criterios de documentación oficial; no se copia un proceso corporativo privado ni se afirma certificación. Estas páginas no incrementan el corpus de proyectos reales.

| Fuente oficial | URL | Criterio aplicado |
|---|---|---|
| Atlassian, Bug report template | https://www.atlassian.com/software/jira/templates/bug-report | Entorno, severidad, reproducción y resultados esperado/actual; flujo de seguimiento |
| Atlassian, Acceptance criteria | https://www.atlassian.com/work-management/project-management/acceptance-criteria | Criterios claros, comprobables y centrados en resultados, sin prescribir solución |
| GitHub Docs, Syntax for issue forms | https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms | Formularios YAML en .github/ISSUE_TEMPLATE con campos y validaciones |
| Microsoft Learn, Agile workflow in Azure Boards | https://learn.microsoft.com/en-us/azure/devops/boards/work-items/guidance/agile-process-workflow?view=azure-devops | Diferenciar epic/feature/story/task/bug y seguir estados del trabajo |

## Límites

El estilo corporativo no exige contratar Jira ni crear una cuenta externa. Las plantillas opcionales de GitHub usan campos de bug y story; no asignan personas ni proyectos remotos. Los tickets publicados en Markdown siguen siendo el soporte diario del laboratorio.

La documentación técnica de Spring/PostgreSQL/OWASP pertenece a decisiones de arquitectura y validación, no se inserta como pista dentro de incidencias. Los ejemplos del historial no acreditan una ejecución reciente: debe consignarse el SHA y la prueba concreta.
